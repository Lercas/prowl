# Аудит публичных ключей

Первый этап 1.5.0: отдельная проверка ACL Algolia для `domain` и `mobile`.

```sh
prowl mobile owned.apk --audit-public --authorized --format json
prowl domain owned.example --audit-public --authorized --format sarif
```

`--authorized` подтверждает право проверять и исходный объект, и найденные в нём
провайдерские ресурсы. Один этот флаг не включает аудит. Без подтверждения команда
отказывает при разборе аргументов, до чтения источника и обращения к провайдеру.
Флаг не доступен в MCP, LSP, HTTP server и остальных CLI-командах.

Аудит работает после ML, если ML включён. Он использует только победившие
кандидаты и их исходные значения. Нужны тип `algolia-api-key` и application ID из
того же безопасно разобранного объекта JSON, YAML или TOML. Имена свойства ID:
`algolia_app_id`, `algolia_application_id`, `application_id`, `app_id`; регистр и
разделители `_`, `-`, `.` несущественны. Значение — ровно 10 латинских заглавных
букв или цифр. Родительский или соседний объект не считается источником привязки.
Неоднозначные дубли, повреждённый документ и отсутствие привязки запрещают запрос.
JS/TS, XML/plist, строки dex и составные пары из разных файлов пока не связываются.

Проверка посылает один GET собственного ключа в фиксированный HTTPS endpoint
`{applicationID}.algolia.net/1/keys/{key}`. Это документированный способ прочитать
ACL как admin, так и обычным ключом для самого себя:
[Algolia: Retrieve API key permissions](https://www.algolia.com/doc/rest-api/search/get-api-key).
Произвольные endpoint, перебор ключей, индексов и записей, запись данных и переходы
по редиректам отсутствуют. Сетевая защита `safehttp` применяется и к этой проверке.
Ключ неизбежно передаётся провайдеру в заголовке и URL, как требует его API;
сырые URL, ошибки, описания и тело ответа не попадают в отчёт или журнал.

Лимиты одной команды: 32 попытки запросов, четыре одновременных запроса,
64 КиБ ответа, timeout не более 10 секунд на запрос. Кеш объединяет одинаковые
пары application ID + ключ по SHA-256, без хранения исходной пары в ключе кеша.
Ошибки не кешируются как достоверный результат; повторные попытки тоже расходуют
общий лимит. У каждого запуска свой кеш и бюджет.

## Значения результата

JSON хранит результат отдельно в `public_key_audit`, SARIF — в `properties`;
отдельные occurrences сохраняют собственный результат. Pretty выводит строку
`public key audit`. Поля `verified` и `verification` аудит не устанавливает.

| Статус | Что установлено |
|---|---|
| `excess_permissions` | ACL содержит известные права сверх `search` |
| `search_only` | В ответе ACL состоит только из `search`; другие ограничения не оценены |
| `inconclusive` | Привязку или ACL нельзя достоверно установить |

Неизвестные права, повторные ACL-поля, несовпадающий ключ в ответе, неоднозначный
JSON, слишком большой ответ, HTTP-отказ, ошибка сети и исчерпанный бюджет дают
`inconclusive`. Провайдерские сообщения и неизвестные права не отражаются в отчёте.
Такой результат добавляет диагностический код `public_key_audit_inconclusive`,
делает покрытие неполным, приводит к exit 2 и запрещает обновление baseline.
Неподдерживаемые типы не получают фиктивный результат аудита.

`search_only` не удостоверяет безопасность данных, referrer/IP-ограничений,
индексов, срока жизни или rate limit. Отсутствие разрешённого чтения ACL не
доказывает, что ключ мёртв или безопасен. `excess_permissions` не отличает
встроенный admin-ключ от пользовательского ключа с широкими правами.
Список известных ACL основан на
[официальной схеме Algolia](https://www.algolia.com/doc/rest-api/search/add-api-key).

Обычные severity и `--fail-on` сохраняются: поиск ключа и наблюдение его прав —
разные факты. `--audit-public` нельзя совмещать с `--verify`, `--verify-all`,
`--verified-only` и `--fail-on-verified`: существующие verifier-профили могут
включать другие операции. Базовые результаты и policy scope без нового opt-in
не меняются; включённый аудит получает собственную revision в coverage.

## Границы готовности

Проверены локальные транспортные, parser, cache/concurrency, pipeline и CLI
контракты. Запросов к чужим ключам или реальным провайдерам при квалификации
не было. Проверка реального аккаунта требует отдельного разрешённого ресурса.
