# Декодирование и нормализация

Детектор проверяет секреты не только в буквальном тексте. Дополнительные представления
строятся локально, без исполнения JavaScript, вызова shell и обращения к провайдерам.
Для live-проверки по-прежнему нужен отдельный `--verify`.

Поддерживаются следующие формы:

- Base64 с обычным и URL-алфавитом, с padding и без него; hex с печатным текстом внутри.
- Вложенные кодировки до трёх слоёв; gzip/zlib внутри base64.
- Base64 `user:password` под точным именем `auth` или `_auth`, например в Docker config
  и `.npmrc`. Просто вхождение подстроки `auth` в имя не считается достаточным контекстом.
- JSON внутри JSON-строки, escapes `\uXXXX`, `\xNN`, `\/` и экранированные кавычки.
  Это ограниченное текстовое представление, а не полный парсер всех языков и escapes.
- Склейка строк с одинаковыми кавычками и оператором `+`, включая соседние строки.
- Начало значения в YAML block scalar `|`/`>` и markdown-выделение возле присваивания.
- Статические числовые `String.fromCharCode(...)`, литеральный spread-массив и
  `String.fromCharCode.apply(null/undefined, [...])`.

Общий нелинейный blob-проход сохраняет только типизированные находки. Если имя внешнего blob не
указывает на секрет, требуется исходная уверенность не ниже 0,9. Для склейки строк
также допускаются только типизированные находки. Уверенность снижается на 5% за такое
косвенное обнаружение; это не означает, что ключ проверен у провайдера.

У находки из нелинейного blob остаётся позиция внешнего blob, а значением становится извлечённый
секрет. Все находки одного внешнего blob делят один диапазон, поэтому сохраняется один
типизированный победитель по уверенности. Нормализованное представление хранит карту
исходных байтов: строка и столбец относятся к исходному файлу. Маскирование включено
по умолчанию; `--show-secrets` явно раскрывает значение и исходный контекст.
Линейный Base64-проход сохраняет отдельные исходные диапазоны. Восстановленный JWT
дополнительно проверяется как JSON-контейнер с typed/именованными generic детьми и
шаблонами; см. раздел о JWT ниже. Generic entropy claims остаются исключёнными.

Ресурсные ограничения являются частью контракта:

| Ограничение | Значение |
|---|---:|
| Длина внешнего кандидата | 16–8192 байта |
| Нелинейное декодирование | 3 слоя |
| Линейные Base64-шаги, включая payload JWT | 4 слоя |
| Внутренние попытки декодирования | 32 на внешний blob, общие для дерева |
| Результат одной распаковки | 256 КиБ |
| Нормализованное представление | 1 МиБ |
| Конструкции нормализации | 4096 |
| Контекст возле конструкции | до 256 байт с каждой стороны |

Глубина и длина кандидата задают область поддерживаемого декодирования. Исчерпание
внутреннего бюджета, лимита распаковки или нормализации помечает результат как неполный.
Повреждённый сжатый поток с уже прочитанным содержимым сохраняет доступные находки и
также помечает результат неполным. Случайный заголовок без распакованных данных этого
не делает. Сканирование учитывает отмену; gzip/zlib readers закрываются.

В JSON/SARIF неполнота передаётся существующим маркером `results_truncated` и признаком
`truncated`; CLI завершает такой скан с кодом 2. Неполный результат не считается чистым
сканом даже при отсутствии находок. Лимиты не отключают буквальный поиск в исходном тексте.

Добавлены отдельные percent/HTML-представления: печатные ASCII `%HH` и полные
HTML-сущности с `;`, включая числовые ссылки и именованные символы. `+` остаётся
плюсом; управляющие байты, некорректный UTF-8 и неподдержанные ссылки не превращаются
в новые границы строк. Декодирование однослойное, без исполнения выражений.

Из этого представления принимаются только типизированные попадания с исходной
уверенностью не ниже 0,9, затем применяется коэффициент 0,95. Произвольный generic-пароль
`Secure%21Pass7` не объявляется равным `Secure!Pass7`: семантика зависит от потребителя.
Старое представление выполняется отдельно, поэтому соседняя HTML-сущность не подавляет
прежнее распознавание JSON/Markdown. Оба прохода делят общий лимит 1 МиБ и 4096 конструкций.
Позиция относится к исходному `%HH`/entity-диапазону, HMAC/fingerprint — к логическому
значению. Индекс очищает также наблюдавшееся исходное написание из метаданных пути.

Пока не поддерживаются generic-значения percent/HTML с неустановленной семантикой,
перевёрнутые и разряженные строки. Обработка JWT описана отдельно ниже.

`String.fromCharCode` разбирается без запуска JavaScript: только числовые литералы с
необязательным знаком, десятичной дробью/exponent, hex/binary/octal и корректными
разделителями `_`. Число округляется как Number, дробная часть отбрасывается к нулю,
затем применяется modulo 65536; кодовые единицы собираются как UTF-16. Семантика —
[ECMAScript fromCharCode](https://tc39.es/ecma262/2026/multipage/text-processing.html#sec-string.fromcharcode)
и [ToUint16](https://tc39.es/ecma262/2026/multipage/abstract-operations.html#sec-touint16).
Это ограниченный текстовый анализ констант, а не доказательство значения программы
при переопределённом `String`.

Внутри восстановленного текста принимаются типизированные значения с исходной
уверенностью не ниже 0,9 и коэффициентом 0,95. Полное generic-значение допускается
только под распознанным секретным именем в присваивании или сравнении, включая обратный
порядок операндов; прежние фильтры и границы длины сохранены. Печатное значение не теряет
внутренние кавычки и разделители; generic-строки с пробелами/управляющими символами
по-прежнему исключаются. Позиция указывает на весь вызов, HMAC — на логические байты
выбранного секрета. Числовые аргументы распознанного статического вызова не выдаются
как пароли по общему контекстному намёку; типизированные и точные совпадения сохраняются.

Для L2 метка поля сохраняется, а в ограниченный контекст проецируется логическое значение:
модель видит строковый литерал вместо списка кодов. Дополнительные данные payload не
декодируются для ML. В JSON с `--show-secrets` `context.line` совпадает с фактическим
контекстом модели (для обратной связи и обучения), `context.original_line` сохраняет
исходную строку, ограниченную прежними 400 байтами. Без явного раскрытия весь `context`
отсутствует. Обычные находки сохраняют прежний формат; новый ключ появляется только
при отличающемся контексте декодированного вызова.

Лимиты одного вызова — 16 КиБ исходного текста, 4096 UTF-16 единиц и 128 байт одного
числового литерала. Обнаружение делит общий бюджет 4096 конструкций и 1 МиБ представления
с JSON/Markdown и percent/HTML. Превышение бюджета или повреждённый UTF-16 помечает скан
неполным. При повреждении допустимы доступные типизированные фрагменты, но совпадения
с U+FFFD из такого вызова и весь generic-кандидат исключаются. Самостоятельный корректный
литерал U+FFFD не считается повреждением. Молчаливой подмены секретного значения нет.

Переменные, арифметические аргументы, массивы с пропусками, комментарии между токенами,
склейка нескольких вызовов/литералов и произвольные `.apply`-формы не вычисляются.
Пробелы, табуляция и CR/LF между токенами разрешены; legacy octal без `0o` не
угадывается. URI в кавычках больше не захватывает закрывающую кавычку; снятие inline-backtick
сохраняет границу значения, а не склеивает URI с соседним кодом. Это исправляет логическую
идентичность обычной и числовой записи. Для ранее ошибочно захваченного значения URI
fingerprint меняется вместе с исправленным значением; формула fingerprint не менялась.
JavaScript-движок для продукта не нужен. Квалификация —
[char-code](evidence/1.5.0-charcode-20261114.json).

Таблицы Markdown/Jira проверяются отдельным ограниченным разбором ячеек. Поддержаны
вертикальные строки `| Password | Kx7#mPq2 |`, Markdown-заголовки с обязательной строкой
выравнивания и Jira-заголовки `||User||Password||`. В горизонтальной таблице внешние `|`
необязательны. Без заголовка вертикальная строка требует обоих внешних разделителей.
Имя столбца передаётся ML как имя поля; строка контекста и позиция остаются исходными.

Ячейка сохраняет запятые, точки с запятой и внутренние кавычки. До двух сбалансированных
слоёв выделения, кавычек, backticks или Jira `{{…}}` снимаются; `\|` внутри ячейки
становится логическим `|`. Это ограниченная текстовая семантика, а не полный Markdown
renderer. Пароли с пробелами пока не поддерживаются. Действуют прежние нижние границы:
пароль — 6 символов, токен — 20, hex-ключ — 32; метаданные и placeholders исключаются.
Typed-детекторы сохраняют приоритет перед generic-попаданием.

Разбор ограничен 4096 подходящими строками и 1 МиБ их исходного текста, строкой в 8192
байта и 32 столбцами. Это отдельный бюджет без создания нормализованной копии документа.
Превышение строкового/колоночного лимита в активной таблице с секретным столбцом либо
строке с распознанной секретной меткой помечает скан неполным. Остальной буквальный
поиск продолжается. Квалификация — [таблицы](evidence/1.5.0-tables-20261114.json).

Именованные присваивания включены в основной конвейер: `SECRET_KEY`, `*_TOKEN`,
`API key`, присваивания через `os.environ` и `=>`, quoted-пароли с запятыми и точками
с запятой, Basic-схема внутри кода с проверкой декодированной пары. Новая generic-ветвь
проверяет имя, случайность значения и исключает метаданные, placeholders и ссылки на код.
Нижняя граница токена — 20 символов, hex — 32; короткие значения этим путём не покрыты.
Бюджет ограничивает также отклонённые regex-кандидаты: исчерпание помечает скан неполным.
С переносимой ML-моделью subset даёт 1608/2094 и прежние 61/982 ложных срабатываний;
индекс включён/выключен. Подробности —
[квалификация именованных присваиваний](evidence/1.5.0-named-assignments-20261114.json).

Сравнения с литералом проверяются отдельно от присваивания: `password == "…"`,
`cfg['password'] != '…'`, `"…" === cfg.api_key` и `!==` в обоих направлениях.
Поддержаны ASCII-идентификаторы, свойства через точку и простой индекс с quoted-именем.
Это текстовый анализ кандидата, а не доказательство, что сравнение выполняет аутентификацию.
Уверенность generic-кандидата — 0,6; типизированные детекторы сохраняют приоритет.

В quoted-операнде допускаются обычные/обратные кавычки, экранированные кавычки,
backslash, `\xNN` и печатные `\uXXXX`. Исходная строка и диапазон не теряются;
HMAC строится по логическому значению. Неизвестные escapes, управляющие escapes,
placeholders, метаданные поля и известные шаблонные ссылки исключаются. Новая ветвь не принимает f/r/b-префиксы,
конкатенацию, вызовы методов и многострочные операнды; прежние независимые детекторы
продолжают работать. Нижние границы generic-значений остаются прежними.

Имя поля передаётся ML также при обратном порядке операндов. При совпадении одинаковых
контекстных кандидатов сохраняется распознанная метка поля. Поиск использует тот же
планировщик regex-окон и общий бюджет named-кандидатов, включая отклонённые совпадения;
исчерпание остаётся неполным сканом и блокировкой `guard`. Подробности —
[квалификация сравнений](evidence/1.5.0-comparisons-20261114.json).

Локальная квалификация `c24455b`: на ProwlBench subset recall вырос с 1580 до
1585/2094 при прежних 61/982 ложных срабатываниях; старый baseline не менялся.
На GOROOT полный конвейер в трёх парах даёт медиану 9,237 → 8,696 с относительно
`a5347b0`, B/op +5,64%, allocs/op +6,37%. Это результат данного корпуса и окружения.

В этом замере число результатов 1132 → 1133 включает один дополнительный маркер
неполноты у `debug/buildinfo/testdata/go117/go117.base64`. Частично распакованные
фрагменты обёрнутого бинарного base64 могут консервативно помечаться неполными;
это не дополнительная находка секрета. Такое поведение требует учитывать данные
этого вида при оценке применимости CLI в CI.

Проверки, точные ревизии и границы доказательств приведены в
[отчёте декодирования и нормализации](evidence/1.5.0-decode-views-20261114.json).

Регрессии целостности отдельно фиксируют: короткий или низкоэнтропийный вывод реального
gzip/zlib с повреждённой контрольной суммой сохраняется вместе с признаком неполноты.
Этот признак не снимается из-за бинарного вида обрезанного префикса. Порог энтропии
не является доказательством отсутствия секрета в непрочитанном хвосте. Неоднозначные
случайные заголовки с непустым выводом по-прежнему могут давать консервативную диагностику.

Checksum-ошибка после корректно разобранного пустого deflate тоже помечает результат
неполным: в gzip она может остановить чтение до следующего member, содержащего секрет.
Корректный пустой поток остаётся чистым; случайные заголовки без распакованного вывода
и без подтверждённой checksum-ошибки не объявляются документом.

На GOROOT 1.27.4 прямой per-item бенчмарк дополнительно помечает неполной таблицу
`cmd/vendor/rsc.io/markdown/entity.go`: 2083 конструкций старого представления и
2013 нового исчерпывают общий предел 4096. Это диагностическая строка, не новая
находка секрета. В сравнении с родительской ревизией остаются 1149 встроенных
совпадений; результаты оконного и полного поиска совпадают. Проверки и границы —
[отчёт percent/HTML и целостности](evidence/1.5.0-text-encoding-integrity-20261114.json).

Квалификация таблиц (`e9f52e1`): ProwlBench subset со встроенной переносимой ML-моделью
даёт 1611/2094 против 1608/2094 у `9961905`; ложные срабатывания остаются 61/982,
прежний baseline и допуск не менялись. Проверены полный Go suite, lint, race, минимальный
Go 1.26.11, fuzz и 17 нативных scan/guard-проверок. Старые пользовательские модели и
конфиги клиентов не менялись.

Локальное сравнение производительности с `9961905` в трёх чередующихся парах на
12044 файлах GOROOT: время +1,33%, B/op +0,27%, allocs/op +15,05%; все прежние допуски
соблюдены. 1154 строки результата в обоих вариантах включают два прежних маркера
неполноты. Первая реализация не прошла лимит аллокаций; хранение отложенной строки
перенесено из heap в значение, после чего повторён полный замер. Это допуск текущего
изменения относительно родителя; он не заменяет квалификацию опубликованного релиза.

Квалификация сравнений (`8d43a48`): полный Go suite и lint на Go 1.27.4, detect/scan
на Go 1.26.11, целевые race-тесты сравнений/таблиц и fuzz прошли. Проверены 29 нативных
scan/guard-сценариев и два скана индекса: исходное/экранированное значение имеют одинаковый
HMAC, в приватном состоянии нет plaintext. 50001 отклонённое regex-совпадение приводит
к неполному скану и блокировке guard, а не к чистому результату.

ProwlBench subset со встроенной моделью: 1616/2094 против 1611/2094 у `3c62200`,
ложные остаются 61/982; новых отрицательных ID и потерянных прежних ID нет.
Baseline и пороги не менялись. В трёх чередующихся парах на GOROOT время +10,20%,
B/op +0,42%, allocs/op +0,02%; прежние допуски соблюдены, 1154 строки результата
в обоих вариантах. Это локальное сравнение с предыдущей версией, не допуск публикации.

Квалификация char-code: 1987 литералов в пределах лимита дали одинаковые кодовые единицы
на Go 1.26.11, Go 1.27.4 и Node.js 22.23.4. Node запускался только как независимый oracle
на сгенерированных тестовых данных. Числовые литералы длиннее 128 байт не включались
в это сравнение; отказ с неполнотой проверен отдельной регрессией, лимит не повышался.

Полный Go suite, lint, целевые race-тесты, минимальный Go и fuzz прошли. Нативная матрица:
58 scan/guard-сценариев, три проверки раскрытия контекста по явному флагу и два скана
индекса. ProwlBench subset со встроенной моделью сохранил 1616/2094 и 61/982, без новых
или потерянных ID. Это локальная квалификация; пользовательские модели, клиенты и
production не менялись, релиз не публиковался.

Сравнение `2ccfb2f` с `9504f07` в трёх чередующихся парах на 12044 файлах GOROOT:
время +0,09%, B/op +0,10%, allocs/op +0,03%; прежние допуски соблюдены, по 1154 строки
результата, включая прежние маркеры неполноты. Это L1 + bundled rules без ML/verify,
локальное сравнение с родителем; оно не заменяет фиксированный релизный baseline или
приёмку опубликованного артефакта.

## Секреты в payload JWT

JWT/JWS с JSON claims теперь считается контейнером: нахождение самого токена не
скрывает typed-секреты и именованные generic-кандидаты внутри payload. Bare entropy
claim вроде случайного `sub` не становится самостоятельным секретом. Прежние фильтры
документационных JWT не скрывают независимый пароль внутри них; выключение типа `jwt`
не выключает остальные детекторы payload.

Три compact-сегмента распознаются отдельно от overlap pass. Header должен быть
JSON-объектом с непустым строковым `alg`; payload — UTF-8 JSON-объект. Допускаются
JSON whitespace и пустая signature у unsigned-токена. Подпись, `alg`, issuer,
роль и сроки локально не аутентифицируются. JWE с пятью сегментами, detached payload,
JWS JSON serialization и произвольные внешние ключи не обрабатываются этим проходом.
Проход не выполняет код, не расшифровывает содержимое и сам не обращается к сети.

Для payload применяется обычный локальный детектор, включая нормализацию escapes
и bounded декодирование. Дубли claims не схлопываются в map значений. Неполнота
вложенного прохода сохраняется; malformed JSON/Unicode, лимит размера/глубины/работы
или выхода — неполный скан и запрет baseline/блокировка guard.

Встроенная таксономия и named-кандидаты проверяются независимо от шаблонов.
При подключённом template engine внешний или bundled-шаблон получает исходный
JSON payload; структурные matchers сохраняют объект целиком. При наличии JSON
escapes дополнительно проверяются логические строки с именами полей. Извлечение
из синтетического wrapper запрещено: normalized hit должен лежать внутри одного
scalar. Raw hit с escaped spelling заменяется логической проверкой.

Шаблонная находка получает stage `rule/jwt-payload` и проецируется в исходные
Base64-диапазоны до ML, наблюдения индекса и формирования отчёта. Вложенный JWT
в escaped JSON-строке использует байтовую карту Unicode escapes, а не синтетические
координаты. `--show-secrets` раскрывает точное логическое значение; декодированный
контекст этой шаблонной находки в отчёт не добавляется. Порядок colliding-шаблонов,
приоритет checksum builtin, отключение и фильтрация правил сохраняются.
`--reconstruct` также проверяет JWT, восстановленный bounded parser из доказанных
JS/TS строковых выражений. Линейный Base64 также передаёт восстановленный JWT
в payload-проход. Нелинейные внешние кодирования и нормализованные views
всего JWT остаются отдельной задачей.

Общие для одного item и вложенных JWT пределы: 4096 сырьевых compact-конструкций
на проход, до 128 распознанных payload, 1 МиБ encoded header+payload work, до
8192 байт на каждый header/payload и три уровня JWT. Цепочка доказательств — не
более четырёх Base64-слоёв; общий предел находок не повышен. Другие декодеры сохраняют
собственные прежние пределы.

Во встроенном проходе escaped JSON-строки обходятся потоковым parser без схлопывания дублей. Значение
декодируется целиком, включая кавычки, backslash, управляющие escapes и корректные
UTF-16 surrogate pairs. Для этих строк исходный диапазон покрывает весь исходный
JSON scalar в encoded payload; в identity/ML попадает логическое значение.
Обход ограничен 4096 JSON tokens, глубиной 64 и 256 escaped scalar-проверками на
item с вложенными JWT; строка до 4096 байт. Префикс credential не выдаётся вместо
непрочитанного полного значения; непроверенные строки сохраняют неполноту.
Шаблонная канонизация также ограничена 4096 JSON tokens на view, глубиной 64 и
4096 байтами на строку; она использует уже ограниченный общий набор payload.
Все raw/normalized rule hits, включая затем отфильтрованные и повторные, расходуют
оставшийся общий бюджет template engine. Исчерпание сохраняет неполноту.

Для прямого JWT координаты дочерней находки относятся к полным Base64-квантам исходного payload;
evidence хранит исходные encoded ranges, значение и HMAC — логический секрет.
ML получает декодированный контекст и распознанное имя поля, с прежними лимитами
контекста и фильтрацией модели. Child не наследует checksum/ML-exemption JWT:
собственный checksum сохраняется только у самого child-типа. Модель и порог не менялись.
По умолчанию plaintext claims/context не сериализуются; явный `--show-secrets`
сохраняет прежнюю семантику раскрытия.

Decoded child не использует claims или окружающий конфиг как доверенную пару для
`--verify`/`--audit-public`. Standalone verifier может проверить сам найденный ключ;
verifier, требующий companions, получает отсутствие безопасной привязки. Новый проход
не добавляет парсинг конфигурации для public-аудита внутри claims.

Основания формата: [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519) и
[JWS compact serialization, RFC 7515](https://www.rfc-editor.org/rfc/rfc7515).
Это анализ представленных байтов, не утверждение о действительности JWT.

### JWT в реконструированном выражении

`--reconstruct` передаёт доказанную строку в общий Pipeline. Для её JWT payload
проверка JS identifier учитывает proof исходного строкового выражения; обычный
некавыченный код сохраняет прежнюю фильтрацию. Пароль проходит обычный ML с логическим
значением и именем поля. Opt-in, поддерживаемые расширения и запрет shadowed decoders
остаются прежними.

Находка указывает на целое исходное выражение. Ранее созданные Base64-доказательства
переносятся на ту же область с transform
`reconstructed/<expression-transform-chain>/<decode-step>`; отдельные evidence
показывают исходные литералы и ссылки на bindings. Проекция выполняется до ML и
приватных наблюдений верификации. Приватный callback сохраняет только существующие
метаданные места и вердикта. JSON-колонка остаётся байтовой, SARIF — UTF-16.
При обычной агрегации эти доказательства сохраняются также во вложенных occurrences.

До исправления восемь вариантов JS/TSX выдавали виртуальный payload proof; после
исправления только evidence во всех восьми ещё терялся пароль. Исправление обоих
путей `d4378e9` (main `140fac5`, одинаковые исходники) прошло full Go, scan race,
Go 1.26.11, lint и fuzz 15332. Native 46/46 под проверенным OS network deny:
concat, array join, `atob`, `decodeURIComponent` в JS/TSX, ML, внешние и bundled
шаблоны, opt-in-off, SARIF/pretty/reveal, HMAC/private index и baseline при неполноте.
Unit-контроль проверяет исходные evidence до ML и отвергнутый standalone verdict
в приватном наблюдении; payload не расширяет схему этого наблюдения.

проходит три пары (+17,82% времени, B/op −10,64%, allocs −5,39%); он измеряет обычный
Pipeline без включённой реконструкции. Полный digest этого корпуса также сохранён:
419 находок, 85 неполных файлов. Это отдельные доказательства обычного режима и
функциональной реконструкции, без замера throughput последней.
[Evidence](evidence/1.5.0-reconstructed-jwt-20261115.json).

### JWT внутри линейного Base64

Обычный и URL-алфавит, с padding/без padding, поддерживаются для непрерывных encoded
runs. До трёх внешних обёрток и Base64url payload используют максимум четыре шага
source proof. У каждого child сохраняются логическое значение, внутреннее имя поля
для ML и диапазоны исходных Base64-квантов. Внешний носитель может содержать текст
перед JWT; proof охватывает его действительные encoded интервалы. Прежние ограничения
размера кандидата, 8 МиБ Base64-work и исключения known-non-secret blobs сохраняются.

Прямые контейнеры обходятся до остальных декодеров. Бюджет JWT общий на item и
рекурсию: 128 payload, 1 МиБ encoded header+payload и 4096 записей физических
контейнеров. Cache хранит также отклонённые по глубине контейнеры, поэтому другой
Base64-маршрут не получает новую попытку с нулевой JWT depth. Ключ ограничен header
и payload; длина signature не увеличивает хешируемый материал cache. Все найденные
дети добавляются после обычного overlap-pass в рамках прежнего общего match cap.

Claims-aware duplicate сохраняет свою семантику даже при удалённом из таксономии
типе `jwt`: verify/public audit получают отсутствие доверенных companions. Для
приватного индекса логический JWT также используется как материал редактирования
метаданных, в том числе без template engine. Полный token не добавляется в схему
приватного наблюдения. Base64-данные могут давать находку без `--reconstruct` и при
shadowed JS decoder; реконструкция программы в этих случаях не выполняется.

`e0d9ad4` (main `c45fc23`, одинаковые исходники): full Go, detect/scan race,
Go 1.26.11, lint, fuzz 19461 и native 168/168 под проверенным OS network deny.
Проверены четыре варианта Base64 с реальными различиями алфавитов, 1–3 слоя,
пять форматов, ML, builtin/external/bundled, reveal/pretty/SARIF, отключение JWT
output, HMAC/private index и baseline при JSON/Unicode/depth-неполноте. Unit-тест
с отсутствующим JWT type и template engine проверяет приватные метаданные;
loopback-контроль запрещает companion extraction до и после ML.

парах: 11,532 / 9,713 с (+18,72% при лимите +20%), B/op −11,26%, allocs −4,33%.
Полный digest GOROOT сохранён: 419 находок, 85 явно неполных файлов. Это не
