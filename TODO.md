### Движок детекта

Сделано 2026-11-14 (не закоммичено): пакет `internal/linewin` — каждая регулярка запускается
не по всему файлу, а по строкам вокруг своего обязательного литерала. Применимость доказывается
автоматически по синтаксическому дереву; что не доказано — идёт прежним полным проходом.
Подключено к встроенной таксономии (`detect`) и шаблонам правил (`rules`). На исходниках Go
(156 МБ): 34,4 → 6,4 с в один поток, находки идентичны.

- [ ] **Минифицированные и однострочные файлы не ускоряются**: окно — это строка, а строка там
  равна файлу. Нужны окна, ограниченные по байтам, с проверкой касания края. Это основной случай
  для `domain` (JS-бандлы).
- [ ] **Оставшиеся полные проходы.** Без окон идут `telegram_bot_token`, `discord_bot_token`,
  `deepseek_api_key`, `private_key_pem` и 15 регулярок шаблонов из 421 (нет литерала или
  неограниченный класс через строки). `basic_auth_header` формально с окнами, но его литерал
  `//` есть почти в каждой строке кода. Варианты: структурные сигналы из байтового прохода
  (как уже сделано для telegram/discord на уровне файла) или DFA-движок вместо NFA из `regexp`.
- [ ] **Аллокации в `rules.Engine.MatchN`**: `strings.ToLower(text)` — копия всего файла на
  каждый элемент; `Matcher.eval` для `word` заново делает `strings.Contains` по всему тексту,
  хотя Aho-Corasick уже знает, какие слова есть.
- [ ] **Честные цифры скорости в README.** «~310 МБ/с» верно только для файла без единого
  ключевого слова. На реальном дереве было 4,5 МБ/с, стало ~24 МБ/с в один поток.
- [ ] **Бенчмарк на корпусе в CI**: `BenchmarkFindingsCorpus` (`internal/scan`) с порогом
  регрессии; сверка «окна = полный проход» (`TestWindowedEqualsWholeText`) на большом корпусе
  по расписанию.
- [ ] **Глубина декодирования.** Сейчас секреты достаются только из base64 (обычный и URL
  алфавит). Нет hex, percent-encoding, `\uXXXX`/`\xNN`-экранирования, gzip+base64, вложенного
